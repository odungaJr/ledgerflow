- **Multi-tenant data isolation — the biggest change in this project's history, planned before any code was touched given real financial data was at stake.** Previously the whole app was one shared dataset behind a single login; now every registered user gets fully private accounts, transactions, budgets, income, assets, liabilities, and categories. A plan was written and independently reviewed (`.claude/plans/fluttering-growing-sun.md`) before implementation — the review caught real cross-tenant integrity bugs a naive "add user_id, filter everything" pass would have missed, all fixed before shipping:
  - Every domain table (`accounts`, `categories`, `transactions`, `budgets`, `income_entries`, `assets`, `asset_values`, `liabilities`, `liability_values`) got a `user_id` FK via Alembic migration `007`, backfilled to the one pre-existing user (`moses`) and made `NOT NULL`. Deliberately gave *child* rows (`asset_values`, `liability_values`) their own `user_id` too — copied from their already-ownership-checked parent at creation, not scoped only transitively — so every single query in the codebase is the same one-line `.filter(Model.user_id == user.id)`, with no join-based "is the parent mine" logic to get wrong on some future endpoint.
  - Categories are **not** a shared global pool — every new registration gets its own private copy of the same 23 default categories (new `app/services/category_engine.py`), seeded at `POST /auth/register` time. Kept the scoping rule identical everywhere instead of a `user_id IS NULL` special case, at the cost of 23 duplicate rows per user (accepted consciously).
  - The review caught: `categories.name` and `transactions.fingerprint` had **global** unique constraints that would've let two users collide on the same category name or import fingerprint — now `UNIQUE(user_id, name)` / `UNIQUE(user_id, fingerprint)`. Several endpoints resolved a category **by name** to populate a foreign key (budgets, income entries, transaction category patches) completely unscoped — fixed every one, since otherwise user B could point a budget at user A's category row just by typing the same name. Transaction import now verifies the target account actually belongs to the caller before importing into it. `income_engine.ensure_recurring_occurrences` picked up a `UNIQUE(series_id, expected_date)` constraint while its signature was already changing, closing a pre-existing (single-tenant-era) race in recurring-income generation.
